Check your answer (open only after you have your own)

Root cause: worker v3.1.0, deployed at 08:50, keeps shipment lookups in memory with no size limit. Memory climbs from about 40% to 100%. At 10:12:20 the worker is OOMKilled and then crash-loops (3 OOM kills by 10:29).

Proof line: 10:12:20 ERROR [worker] container OOMKilled (memory limit 512Mi, usage 512Mi). In metrics-2042.csv, worker_memory_pct rises steadily from 08:50, hours before anything breaks.

Symptoms: queue backlog (up to 7,600), stale shipment status, and the many ui-bff "out of date" warnings (the loudest lines).

Not the cause: the ui-bff v1.9.3 deploy at 10:05 (a footer text change; it is the newest deploy, but memory was rising long before), the certificate warning, and disk 78%. Note that error_rate_pct stays flat: the error rate would not have caught this.

Fix now: roll the worker back to v3.0.4 and let the queue drain. Next week: bound the cache (max size or TTL), set a memory alert at 80%, and roll new versions out gradually.

⭐ Takeaway

The loudest error is usually a symptom, and the newest change is not always the cause. Ask for the proof line, check it, and check the order in time. AI summaries sound sure, so verify the numbers.
